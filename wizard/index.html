Parseltongue // sealed notes

Encrypt a message under a shared code, then hide it inside one that looks completely ordinary. Local-first. No accounts, no relay, no server that could read it.

crypto XChaCha20-Poly1305 · Argon2id runs offline license AGPL-3.0

Three steps

No identities, no key exchange, no setup. Two people, one code, one message that reads as unremarkable.

01 — you
Write the real message and a cover

The secret gets encrypted under a code. The cover is whatever you'd plausibly say — "running late, see you there."

02 — you
Send the cover one way, the code another

The message goes by chat or email. The code goes by voice, or any channel the first one isn't. This separation is the security.

03 — them
They read the hidden message

One command, or one tool call, with the message and the code. Everything happens on their machine.

The payload rides as invisible characters alongside your cover text. A reader sees the cover and nothing else — the example below is a real 495-character artifact carrying a sealed note.

Encrypted vs merely hidden

These are different things and conflating them is the most common way people get hurt. Both layers are present, doing different jobs.

■ encryption — makes it secret
  • XChaCha20-Poly1305 over your message
  • Key from Argon2id over the shared code
  • Without the code it is unreadable, full stop
  • Tampering is detected, not silently accepted
□ concealment — makes it look ordinary
  • Invisible Unicode carrying the ciphertext
  • Buys deniability against a casual reader
  • Provides zero secrecy on its own
  • Anyone looking for it will find it

Encode something without encrypting it and anyone who notices the hidden characters reads it with no key at all. That is why this page has no "hide my text" button — the capability is absent rather than warned about.

The emoji decoder consumes every emoji it is given, so a cover message containing one corrupts the payload. It is standalone or nothing.

Is something hidden in this?

Paste any message. This finds invisible characters, extracts a sealed note if one is present, and tells you what you're holding. Runs entirely in this page — nothing is sent anywhere, and no code is asked for because nothing here decrypts.

At a terminal

The code is typed at the terminal and the message prints there. Nothing passes through an agent or a conversation transcript.

Hide a message

# write the secret to a file first, so it stays out of shell history
$ parseltongue-capsule conceal --in secret.txt \
    --cover "running late, see you there" \
    --out message.txt

Prints the artifact and a generated code of about 67 bits, like gray-dock-perch-8937-garlic-poem-cobra. Words, not base64 — it has to survive being read down a phone line.

Read one

$ parseltongue-capsule reveal --in message.txt
Decrypt code: ****************
--- hidden message ---
east gate, 0400
--- end ---

See the options

$ parseltongue-capsule styles      # carriers and what each looks like
$ parseltongue-capsule help        # everything else

From an AI assistant

The same operations as MCP tools, for when you are already working in a conversation. 

conceal_options  { secret_length, with_cover_text }
    → the carrier styles, with sizes and what each reveals

conceal_message  { secret, cover_text, style?, code? }
    → the one artifact to send, plus the code

reveal_message   { artifact, code }
    → the hidden message
▲ the trade-off, stated plainly

Anything passing through a conversation is retained in that conversation's transcript — the artifact, the code, and the revealed message. That is a copy you did not explicitly choose to make.

It is still the right default, because a tool that hands back a file path instead of your message is useless for reading it. But for anything that genuinely matters, use the terminal.

The mistake that undoes everything

▲ send the code a different way

If the code travels in the same channel as the message, there is no protection whatsoever. Whoever reads that channel reads both, and the encryption was pointless.

This is the realistic failure, not an exotic one. Codes are word-based precisely so you can say one out loud instead of giving up and pasting it under the message.

What it does not defend against

ThreatWhy not
A compromised deviceIf the machine writing or reading the message is owned, so is the message. Encryption cannot fix a keylogger.
Someone looking for steganographyInvisible characters are trivially detectable — the Check tab finds them instantly. Concealment defeats a skim, not an analyst.
A weak or reused codeAnyone holding the artifact can try codes offline with no rate limit. Argon2id makes each attempt expensive; it cannot rescue a guessable code. Reuse means one break reads everything.
ReplayA message reopens every time. There is no freshness check, so a captured artifact can be delivered again later. Put a date inside the message if that matters.
Knowing who sent itA shared code proves the sender knew the code — nothing more. Anyone else who knows it could have written the message.
Platforms that strip invisible charactersSome do, silently. The recipient gets your cover message with nothing inside. Send it as a file if a channel keeps eating it.
What you do nextPasting the revealed message elsewhere makes a copy none of this protects.

There is no recovery

Lose the code and the message is gone. No reset, no escrow, nobody to ask — a recovery path is a backdoor with better branding. For the identity-based mode there is a backup command, and using it is not optional.

Honest status

This has had a careful self-review, not an external audit. Established primitives are used throughout and nothing was hand-rolled, but one person wrote the code and one person reviewed it — and that review did find a real flaw in the first attempt. Weigh it accordingly.
